# Mirage defender notification

## Live notification smoke test

With the main backend and webhook tunnel running, start one scripted cage run with `POST http://localhost:8787/cage/start`. This emits watcher verdicts into the main server's event bus. In live voice mode, a medium-priority verdict sends an iMessage; a later high-priority verdict sends an escalation iMessage and places a real call. The analyst should answer, receive a six-digit code after `send_code`, read it back, and hear the briefing only after `verify_code` succeeds. Check `/api/audit` for `notification.priority_checked`, `call.mirage_outbound`, `call.verified`, and `mirage_briefing.delivered`; `/api/calls` must show the latest session as `verified: true`. The outbound-call event alone does not prove that verification or briefing succeeded. Run at most two agents while live voice or Photon delivery is enabled.

The scripted dashboard emits the effective `pass` verdict when its watcher is off, so the contrast run does not trigger an analyst notification. The live cage also emits `pass` for watcher-off runs.

The main server subscribes to `session.started`, `tool.call`, and `watcher.verdict` on its shared event bus. `pass` needs no alert, even for Droid. A suspicious (`mirage` or `block`) action from an actual Droid attacker is always **high priority**, regardless of watcher score: it sends a Photon iMessage followed by an immediate ElevenLabs call. If a requested Droid member falls back to a scripted attacker because Factory credentials are missing, the session identifies itself as scripted and follows the scripted policy. For other attackers, a `mirage` verdict with watcher score below `0.9` is **medium priority** and sends one iMessage with the session ID, with no call even when the run ends. A `block` verdict, or a `mirage` verdict with score at least `0.9`, is **high priority** and sends an iMessage followed by a call. If a session escalates from medium to high, it sends a second, high-priority iMessage before calling. Duplicate verdicts do not repeat a successful call; a failed call can be retried on a later high verdict. Separately, a low-severity Batman incident that was automatically fixed and verified clean sends only a summary text with its ticket ID. This is an operational alert priority, not a measured claim about real-world impact. Outgoing messages never include attacker text or watcher reasons.

`VOICE_MODE=mock` keeps the offline demo: `npx tsx server/voice/demo-notification.ts`. With `VOICE_MODE=live`, the server validates Photon, ElevenLabs, the webhook secret, and a **real registered analyst number** at startup. It will fail instead of silently logging mock notifications. Set `PHOTON_MODE=live`, `PHOTON_CHANNEL=imessage`, `PHOTON_PROJECT_ID`, `PHOTON_API_KEY`, `ELEVENLABS_AGENT_ID`, `ELEVENLABS_API_KEY`, `ELEVENLABS_PHONE_NUMBER_ID`, `VOICE_WEBHOOK_SECRET`, and `ANALYST_PHONE`. The analyst number must have role `analyst` in `data/users.json` and must not be a `+1555` demo number. The analyst must have messaged the Photon shared line first if Photon requires inbound iMessage initiation.

The ElevenLabs outbound call sends a Mirage-specific first message and system prompt override. In the agent Security tab, allow **First message** and **System prompt** overrides. Attach four **Webhook** tools to the published agent, all with method `POST`, `Content-Type: application/json`, and a Secret header named `x-batman-secret` whose value matches `VOICE_WEBHOOK_SECRET`:

| Tool name | URL | Body parameters |
| --- | --- | --- |
| `send_code` | `https://<backend>/voice/tools/send-code` | `conversation_id` = `{{system__conversation_id}}`; `caller_id` = `{{system__caller_id}}` |
| `verify_code` | `https://<backend>/voice/tools/verify-code` | Same two system variables; `code` is a six-digit string supplied by the caller |
| `mirage_briefing` | `https://<backend>/voice/tools/mirage-briefing` | Same two system variables |
| `contain` | `https://<backend>/voice/tools/contain` | Same two system variables; `decision` is exactly `contain` or `hold`, selected from the verified analyst's spoken answer |

Configure `conversation_id` and `caller_id` as dynamic-variable values in the tool body, not values generated by the agent. The server uses the conversation ID to pin an outbound call to the dialed analyst and its Mirage trigger. It sends the code to that registered number and releases the briefing only after server-side verification. `mirage_briefing` is read-only. The `contain` tool accepts only a verified analyst on a Mirage outbound call. `contain` requests the cage stop; the actual outcome appears later in `run.summary`. `hold` records the choice without stopping the run. Never provide a session id from the model in this tool.

The same published `mirage_briefing` tool also serves the verified, server-pinned briefing for an urgent Batman incident. The per-call prompt tells ElevenLabs to report the returned status. When a fix awaits approval, the agent directs the analyst to the Batman console; the published tools do not include a spoken Batman fix-approval tool. `contain` is Mirage-only.

For lower-priority review, the Batman text includes a ticket ID; read its incident and audit trail in the console at `/demo`, `/api/incidents/<ticket-id>`, and `/api/audit`. Its complete step-by-step trace is at `/defense/trace/<ticket-id>` and saved across restarts in `data/defense-traces/<ticket-id>.json`. The Mirage text includes a session ID and, when a signing secret is configured, an opaque eight-character provenance reference. The full signed record is available at `GET /voice/provenance/<session-id>` with the `x-batman-secret` header. The server signs the first watcher trigger with HMAC-SHA256 using `PROVENANCE_SECRET` or, if unset, `VOICE_WEBHOOK_SECRET`, and emits `provenance.signed` when the run summary arrives. Compare the reference with the first eight characters of `fingerprint`; `verified: true` means the stored record still matches its signature. Read the run at `/cage/runs/<session-id>` or `/mirage/forensics/<session-id>`. Host-side cage events are kept in `data/cage-runs/*.jsonl`; in-memory signing records and call verification state are lost on process restart.

The notification event bus, outbound-call map, verification codes, and tool routes must run in **the same backend process**. A standalone voice-only deployment cannot receive Mirage events produced by a separate local server. For an end-to-end live demo, expose the main server (`server/index.ts`) at stable HTTPS and point all four tool URLs there. If a call spans a process restart, its in-memory outbound map and verification code are lost; restart the test call.

For a short Cloudflare Quick Tunnel test on Windows, run the main server with `npm run dev`, run `npx tsx server/voice/tunnel-proxy.ts` in a second terminal, then run `.\.tools\cloudflared.exe tunnel --url http://127.0.0.1:3003` in a third. The proxy forwards only the authenticated voice webhook routes to the main server and exposes `/health` for a connectivity check. Use the printed `https://...trycloudflare.com` address for `/voice/init` and each tool URL. Keep the computer and all three processes running; Quick Tunnel URLs are temporary and change when the tunnel restarts. This test setup is separate from `VOICE_MODE=live`, which still requires the ElevenLabs API key and phone-number ID.
